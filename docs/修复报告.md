# AERA Recovery PIN 解密卡死 — 根因与修复

设备：OnePlus Ace 3 / PJE110 / `astonc` / SM8550 `kalama`
目标 ROM：ColorOS Android 17（sdk 36）
Recovery：AERA `R1.0`，codebase `aera-16.0`
状态：**已修复，真机验证解密可用**

---

## 1. 结论（一句话）

recovery 的 framework VINTF 清单里**没有声明任何 AIDL HAL**，导致
`keystore2` 向 servicemanager 注册时被拒、进程 `SIGABRT` 自杀，
`Decrypt_DE()` 永远拿不到 binder 而无限重试 → 解密卡死。

修复 = 在 `/system/manifest.xml` 声明
`android.system.keystore2.IKeystoreService/default`（以及
`android.hardware.boot.IBootControl/default`）。

---

## 2. 故障证据链

### 2.1 原始故障（已刷入的那版 recovery）

```
servicemanager: Caller(pid=2885,uid=0,sid=u:r:recovery:s0) Could not find
    android.system.keystore2.IKeystoreService/default in the VINTF manifest.
    No alternative instances declared in VINTF.
init: Service 'keystore2' (pid 2885) received signal 6          ← SIGABRT
servicemanager: Caller(pid=919,uid=0,sid=u:r:recovery:s0) Tried to start aidl
    service android.system.keystore2.IKeystoreService/default as a lazy service,
    but was unable to.
init: Control message: Could not find
    'aidl/android.system.keystore2.IKeystoreService/default' for ctl.interface_start
```

pid 919 的 recovery 主进程在 `partition.cpp:841` 的
`while (!android::keystore::Decrypt_DE() && --retry_count) usleep(2000);`
里空转，每秒重复一次 lazy-start —— 这就是"卡在解密步骤"。

### 2.2 为什么"卡死"而不是报错退出

`Decrypt_DE()` 是硬依赖 keystore2 的调用。keystore2 死了 → binder 拿不到 →
返回 false → 重试 → 循环。UI 上表现为无限等待。

## 3. 根因定位过程（关键：一个被证伪的假设）

### 3.1 最初（错误）假设：gatekeeper 起不来

`config/gatekeeper-inputs.json` 里记着
`"build-20 user PIN attempts read DE SP metadata then fail to get Gatekeeper
service; verify not reached"`，于是推断是 gatekeeper 服务没起来。
对应的提交给它加了 `class hal`、删掉 `disabled`、并把
`vendor.gatekeeper.*` 属性塞进 ramdisk prop。

**这个假设被真机测量证伪：**

```
$ getprop init.svc.gatekeeper-1-0
running
$ lshal | grep -i gatekeeper
DM Y android.hardware.gatekeeper@1.0::IGatekeeper/default ... 938
$ cat /prop.default | grep gatekeeper
vendor.gatekeeper.disable_spu=true
vendor.gatekeeper.is_security_level_spu=0        ← 本来就在
```

gatekeeper **一直在正常运行且已注册**。属性本来就在设备镜像的
`/prop.default` 里（第 141–142 行），触发条件成立。
**该项改动是无效的，已全部撤回**（见第 6 节）。

同理被撤回的错误结论还有：`/dev/qseecom` 缺失是阻塞点（实际
`qseecomd` 用的是 `/dev/smcinvoke`）、`android.hidl.memory@1.0.so`
缺失（`BoardConfig.mk` 的重链接表里本来就有）、需要 `group drmrpc`
（节点 owner 是 `system`，uid 匹配即得 rw）。

### 3.2 真根因：framework VINTF 清单为空

设备实际状态：

| 域 | main manifest | 是否读取片段目录 | 结果 |
|---|---|---|---|
| vendor | `/vendor/etc/vintf/manifest.xml` **存在**（空 stub） | ✅ 会读 | gatekeeper ✓ keymint ✓ qseecom ✓ |
| system | `/system/etc/vintf/manifest.xml` **不存在** | ❌ 永不读 | keystore2 ✗ bootctl ✗ |

AOSP `system/libvintf/VintfObject.cpp:460` 的逻辑是：

```cpp
status_t VintfObject::fetchUnfilteredFrameworkHalManifest(HalManifest* out, ...) {
    auto systemEtcStatus = fetchOneHalManifest(kSystemManifest, out, error);
    if (systemEtcStatus == OK) {
        // 只有 main manifest 存在时，才会解析片段目录
        addDirectoryManifests(kSystemManifestFragmentDir, out, false, error);
        ...
    }
    return out->fetchAllInformation(getFileSystem().get(), kSystemLegacyManifest, error);
}
```

常量定义：

```
kSystemManifest            = /system/etc/vintf/manifest.xml
kSystemManifestFragmentDir = /system/etc/vintf/manifest/
kSystemLegacyManifest      = /system/manifest.xml
```

设备上：

```
$ cat /system/etc/vintf/manifest.xml
cat: /system/etc/vintf/manifest.xml: No such file or directory
```

**main manifest 不存在 → 走 else 分支 → 整个 `/system/etc/vintf/manifest/`
目录从未被解析。** 于是 framework 清单只剩 `/system/manifest.xml`，
而它只声明了 `android.hidl.manager@1.2` 和 `android.hidl.token@1.0`
——**一个 AIDL HAL 都没有**。

servicemanager 的校验逻辑（`ServiceManager.cpp`）：

```cpp
static bool isVintfDeclared(const Access::CallingContext& ctx,
                            const std::string& name) {
    bool found = forEachManifest([&](const ManifestWithDescription& mwd) {
        if (mwd.manifest->hasAidlInstance(aname.package, aname.iface,
                                          aname.instance)) { ... }
    });
    if (!found) { ALOGI("... Could not find %s in the VINTF manifest.", ...); }
    return found;
}
```

找不到就返回 `EX_ILLEGAL_ARGUMENT`（"VINTF declaration error."），
keystore2 把它当致命错误 → `SIGABRT`。

### 3.3 vendor 域是天然对照组（诊断成立的最强证据）

同一份 libvintf、同一个 recovery init，vendor 域全部正常、system 域全部失败，
唯一差别就是 **vendor 有 main manifest、system 没有**。

## 5. 修复内容

### 5.1 核心改动（真正生效的部分）

在 `/system/manifest.xml` 追加两个 AIDL HAL 声明：

```xml
<hal format="aidl">
    <name>android.system.keystore2</name>
    <version>1</version>
    <fqname>IKeystoreService/default</fqname>
</hal>
<hal format="aidl">
    <name>android.hardware.boot</name>
    <version>1</version>
    <fqname>IBootControl/default</fqname>
</hal>
```

### 5.2 附带修复（当下非阻塞，但属正确性）

- `android.system.keystore2-service.xml`：原文用 `format="aidl"` 却套
  HIDL 的 `<interface><name>/<instance>` 形状。
  **注意修正**：上游 libvintf **确实**会把
  `<version>×<interface>×<instance>` 转成 fqname
  （`parse_xml.cpp:977-1032`，且显式包含 `HalFormat::AIDL`），
  所以这不是本次启动阻塞点。改成 `<fqname>` 是因为这是 AOSP 自己输出的
  形状、且对未来 meta-version 变化更稳。
- `android.hardware.boot-service.default.xml`：位于 framework 片段目录
  却写 `type="device"`。`HalManifest::addAll`（`HalManifest.cpp:725`）
  对 type 不匹配是**硬失败**，所以该片段当前会被整体拒绝。

### 5.3 刻意不做的事

- **不创建 `/system/etc/vintf/manifest.xml`。** 该目录里还有
  `astonc.keymint.xml`，它是 `type="device"`；framework 片段目录用
  `forceSchemaType=false`，一旦把目录启用，这个 device 类型片段会让
  **整个 framework 清单加载失败**，把所有 framework AIDL 注册一起拖垮。
  启用片段目录是比本 bug 大得多的改动，而 legacy 清单路线已验证可用。
- 不动 `recovery.fstab` 的 FBE 参数。
- 不改 `17` / `2026-09-01` 等被哈希/度量绑定的身份值。
- 不加 `group drmrpc`。

### 应急恢复（不重编，立刻可用）

补丁要重新编译刷入才永久生效，但当前设备刷的是无法解密的那版镜像，
`/data` 取不到。可用 `live-patch.sh` 先让本次会话恢复：

```bash
adb push scripts/live-patch.sh /tmp/
adb shell sh /tmp/live-patch.sh
```

它改的是内存盘 `/system`，**重启即还原**——正因如此，在非自建镜像上跑也安全。
脚本会拒绝 `type` 不是 `framework` 的清单，先在 `/tmp` 生成再校验
（必须仍只有 1 个 `</manifest>`）才替换，原文件备份在
`/tmp/manifest.xml.orig`，避免半截写入把整个 framework 清单搞坏。

接入方式（`BoardConfig.mk`，已加在 `BOARD_RECOVERY_IMAGE_PREPARE`
**最后一步**，确保晚于 AERA 脚本与设备树拷贝）：

```make
BOARD_RECOVERY_IMAGE_PREPARE += && python3 $(DEVICE_PATH)/scripts/fix-recovery-vintf.py $(TARGET_RECOVERY_ROOT_OUT)
```

并已在 `AndroidBoard.mk` 的 `ramdisk_files-timestamp` 依赖里登记，
避免增量构建复用陈旧 ramdisk。

| `astonc.gatekeeper.rc` | 加 `class hal`、删 `disabled` | 服务本来就在跑（pid 938、lshal 已注册），前提被证伪 |
