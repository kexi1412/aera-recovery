## 2. 电池：证据链与本轮改动

### 2.1 已知事实（前轮取证）

- gauge 节点开机 ~16 s 才可读（health HAL 19 次重试，t=15.6s）；UI 在
  t≈13.7s 起来，首帧落在不可读窗口。
- `std::clamp` 把"未就绪"伪装成 0%/100%；十秒一次的轮询让 `--%` 挂满全程。
- run #33 已包含范围检查 + 每秒轮询（补丁在 2026-10-16 上游锚点上应用成功、
  编译通过、断言全绿），**真机仍复现** → 根因不止读法。

### 2.2 本轮假设与对策

| 假设 | 对策 |
|---|---|
| persist 未挂载 → `OPLUS_CHG[MMS_GAUGE] init timeout` 持续 → gauge 一直不就绪 | 恢复 `/mnt/vendor/persist` 挂载（fstab 条目 + post-fs mount + ueventd 搜索路径），随 Wi-Fi 移植落地 |
| 节点始终返回"合理的错误值"或打不开 | `fix-battery-read.py` v2：首轮成功后记一行 "answered after N unreadable poll(s)"；~40 s 仍不可读则每分钟写一行诊断（errno + 各候选节点可读性），直接进 logcat（本镜像 logd 常开） |

v2 的关键代码点：`unreadable_polls` 只在**失败**时自增（成功即清零），
保证"轮询计数 ≈ 秒数"始终成立；诊断路径不阻塞 UI 线程。

### 2.3 判定标准（刷新镜像后）

- 正常：UI 起来后 ≤20 s 内状态栏出现真实电量；logcat 出现
  `astonc: battery gauge answered after N unreadable poll(s)`（N≈2..17）。
- 仍异常：状态栏 `--%` 超过 1 分钟，logcat 必有
  `astonc: battery gauge still unreadable after N poll(s)` 行——**拿着这行
  日志 + §5 的取证包回来**，下一轮可精确定位。

## 3. 重启到 fastboot：看门狗设计

### 3.1 上游链路（2026-10-23 源码复核）

```
UI Action::kRebootBootloader
  → RunLoop 返回 kRebootBootloader
  → [fix-power-handoff] 图形线程 park，结果经条件变量交接
  → RunAeraUi 返回 → aera_ui_host.cpp 写 tw_reboot_arg
  → twrp.cpp reboot() → tw_reboot(rb_bootloader)
  → [fix-reboot-fastboot] Clear_Bootloader_Message()
  → request_power_control("reboot,bootloader") → pause() 永驻
  → init: write_reboot_bootloader() → BCB "bootonce-bootloader" → 重启
```

run #33 在这条链上的前两环都已修复，但真机仍未离开 recovery → 第三环
（init 消费）或其上游仍会失败，且失败是静默的。看门狗把这个静默失败变成
"15 秒后必达 fastboot + kmsg 取证行"。

### 3.2 看门狗实现要点（twrp-functions.cpp 文件局部函数）

- `fork()` 子进程睡 15 s；父进程照常走 `request_power_control()`。
- 子进程**零堆分配**（fork 自多线程进程，电池监控线程仍在跑）：栈缓冲 +
  raw fd；取证行写 `/dev/kmsg`（唯一必然存活的通道）。
- BCB 写入只动 command 槽（前 32 字节，父进程已清空整个结构体）：
  bootloader → `bootonce-bootloader`；fastbootd → `boot-fastboot`。
  这与 `bootloader_message.h` 的 struct 布局一致（offset 0）。
- 终态 `sync(); reboot(RB_AUTOBOOT); _exit(127)`。
- `rb_recovery` 保持不动（必须保留 boot-recovery 命令）。

### 3.3 判定标准

- 正常：Menu → Reboot → Bootloader/Fastboot ≤3 s 内设备重启进对应模式。
- 兜底触发（= init 侧仍有问题）：15 s 后进 fastboot，且
  `dmesg | grep astonc` 有
  `astonc watchdog: init did not consume the reboot in 15 s (misc command "...")`
  ——这一行就是下一轮修复 init 侧的起点。

## 5. 刷入后验证清单（按序执行）

```bash
# 0. 基础
adb shell getprop ro.aera.version && adb shell cat /tmp/recovery.log | tail -50

# 1. 电池（两分钟内完成观察）
adb shell "logcat -d -s AERA_UI | grep astonc | tail -5"
#   期望: "battery gauge answered after N unreadable poll(s)" (N<20)
#   异常: "still unreadable after N poll(s)" → 连同下面整个取证包反馈

#   UI: Network → 扫描/连接；连接后 Quick Settings 显示 SSID

# 3. 重启到 bootloader（fastboot 模式）
adb shell dmesg | grep -c astonc   # 先记下当前 astonc 行数
#   UI: Menu → Reboot → Bootloader
#   正常: ≤3s 黑屏进 fastboot；异常: 15s 后进 fastboot 且
#   fastboot oem/`dmesg` 里有 "astonc watchdog:" 行（重启回 recovery 再取）
#   两者都算"能进"；只有 15s 后仍留在 recovery 才算失败

# 4. 重启到 fastbootd
#   UI: Menu → Reboot → Fastboot → 期望进入 fastbootd（黄色警告头）

# 5. 解密回归（Wi-Fi 模块加载在 fstab 解析期运行，必须确认没拖坏解密）

# 6. MTP 回归（与 Wi-Fi 共享 USB gadget 配置）
#   UI: 挂载 /data 后接 PC，期望 MTP 枚举
```

任何一步失败：抓全量 `/tmp/recovery.log`、`dmesg`、`logcat -d` 三件套反馈。
