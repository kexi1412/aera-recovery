## 3. 重启到 fastboot：看门狗设计

### 3.1 上游链路（2026-10-23 源码复核）

```
UI Action::kRebootBootloader
  → RunLoop 返回 kRebootBootloader
  → [fix-power-handoff] 图形线程 park，结果经条件变量交接
  → RunAeraUi 返回 → aera_ui_host.cpp 写 tw_reboot_arg
  → twrp.cpp reboot() → tw_reboot(rb_bootloader)
  → [fix-reboot-fastboot] Clear_Bootloader_Message()
  → request_power_control("reboot,bootloader") → pause() 永驻
  → init: write_reboot_bootloader() → BCB "bootonce-bootloader" → 重启
```

run #33 在这条链上的前两环都已修复，但真机仍未离开 recovery → 第三环
（init 消费）或其上游仍会失败，且失败是静默的。看门狗把这个静默失败变成
"15 秒后必达 fastboot + kmsg 取证行"。

### 3.2 看门狗实现要点（twrp-functions.cpp 文件局部函数）

- `fork()` 子进程睡 15 s；父进程照常走 `request_power_control()`。
- 子进程**零堆分配**（fork 自多线程进程，电池监控线程仍在跑）：栈缓冲 +
  raw fd；取证行写 `/dev/kmsg`（唯一必然存活的通道）。
- BCB 写入只动 command 槽（前 32 字节，父进程已清空整个结构体）：
  bootloader → `bootonce-bootloader`；fastbootd → `boot-fastboot`。
  这与 `bootloader_message.h` 的 struct 布局一致（offset 0）。
- 终态 `sync(); reboot(RB_AUTOBOOT); _exit(127)`。
- `rb_recovery` 保持不动（必须保留 boot-recovery 命令）。

### 3.3 判定标准

- 正常：Menu → Reboot → Bootloader/Fastboot ≤3 s 内设备重启进对应模式。
- 兜底触发（= init 侧仍有问题）：15 s 后进 fastboot，且
  `dmesg | grep astonc` 有
  `astonc watchdog: init did not consume the reboot in 15 s (misc command "...")`
  ——这一行就是下一轮修复 init 侧的起点。

## 8. Run #34 真机结果与 v3 修正（2026-10-24 晚）

### 8.1 真机结果

WiFi 不可用、解密 /data 失败、fastbootd 不可达；电池仍异常。
**#33 可解密、#34 不可解密——受控变量只有一处：fstab 解析期的模块加载。**

### 8.2 根因（kernel_module_loader.cpp 逐行复核）

fstab 解析期运行的 `Load_Vendor_Modules()`：

1. `Try_And_Load_Modules("/vendor/lib/modules")`——该路径是指向
   /vendor_dlkm 的**符号链接**，`Copy_Modules_To_Tmpfs` 把整个
   vendor_dlkm 模块目录拷进 tmpfs；随后又对 /vendor_dlkm 再拷一次；
2. `mount(/tmp 副本, 模块目录, MS_BIND)` 把 tmpfs 副本 **bind-mount 盖在
   真实模块目录上**，且 `UnMount_By_Path` 找不到对应分区、绑定从不拆除；
3. 结束时 **`ven->UnMount(); ven_dlkm->UnMount(MNT_DETACH);
   sys_dlkm->UnMount()`——把 /vendor、/vendor_dlkm 整个卸载**。

后果链：keymint 之后惰性 dlopen /vendor 库失败 → keystore2 → **解密死**；
cnss2 探测时无法经 /vendor/firmware_mnt 解析 amss.bin → **wlan0 永不出现**。
fastbootd 不可达是解密卡死连带（UI 未释放）。dc9122f 当年的"模块加载导致
解密故障"归因——方向是对的，只是当时把它错怪在了解密缺陷上。

### 8.3 v3 修正：post-decrypt-only

- `TW_LOAD_VENDOR_MODULES` / `AERA_LOAD_VENDOR_MODULES` **移除**（连同
  EXCLUDE_GKI）：partitionmanager.cpp:764 的调用整体编译掉，**解密前的
  启动路径与已验证的 #33 逐字节一致**。
- `TW_POST_DECRYPT_MODULES` / `AERA_POST_DECRYPT_MODULES`（aera_config.mk:125
  映射）携带同一 9 模块列表：`Load_Post_Decrypt_Modules()` 从
  Decrypt_Data() 成功路径（partitionmanager.cpp:2665）调用，逐模块
  `finit_module`（无 fork、无 bind-mount、无 tmpfs 全量拷贝），列表顺序即
  依赖序（finit_module 不解析 modules.dep）。
- 新补丁 `scripts/fix-post-decrypt-stage.py`：上游的 staging 只在已被编译掉
  的 `Load_Vendor_Modules()` 里，补丁给 `Load_Post_Decrypt_Modules()` 加
  **按需 staging**——先挂 /vendor、/vendor_dlkm、/mnt/vendor/persist
  （cnss2 探测要 /vendor/firmware_mnt 的 amss.bin；kiwi_v2 要 persist 的
  WCNSS_qcom_cfg.ini），再 `Stage_Post_Decrypt_Modules()`；挂载保持（与
  #33 会话状态一致）；stage 标记文件保证 partitionmanager.cpp:4045 的
  replay 路径幂等。
- CI：门禁反转回 post-decrypt 形状（TW_LOAD 必须缺席、TW_POST 必须在场、
  模块列表依赖序断言、两份列表一致断言）；补丁步骤加 staging 断言；二进制
  检查加 "Staging post-decrypt modules" / "post.decrypt.modules" /
  on-demand 标记字符串。
- beforemodules.sh 保留入树（零成本，记录装载顺序），但不再被调用。

### 8.4 遗留观察点（下轮真机）

- WiFi 首次自动连接可能发生在解密前（early session），模块未加载会失败
  一次；解密后加载完成，wlan0 出现，supplicant 的 sh 包装循环会退出并补上

  条目即可。
- 电池：persist 挂载已在，若仍异常，logcat 的

## 9. 设备现场取证与 v4（2026-10-24 深夜，adb 实测）

run #34 仍在设备上时接入 adb，完成了一轮完整的现场取证与活体实验。
**本轮把三个问题的根因全部钉死，并用 insmod/remoteproc 活体验证了修法。**

### 9.1 解密（推翻 §8.2 的机制，结论不变）

`recovery.log:278`：`Unable to decrypt metadata encryption`，而
keystore2/keymint 全部 running（`init.svc.vendor.keymint-qti=running`，
crash_count=0）。真正的机制是 **Load_Vendor_Modules() 的运行期安全补丁
覆盖块**：它挂 /system_root 并把 security_patch 从钉扎的 2026-09-01
resetprop 成 ROM 的 2026-10-01；KeyMint 按操作时评估 OS 补丁级，元数据
密钥（9 月策略下封装）解包失败。§8.2 的"卸载 /vendor"机制存在但不致命
（vendor HAL 在覆盖前已启动）。

### 9.2 电池：ADSP 未启动（新根因）

- v2 诊断行首功：`battery gauge still unreadable after 540 poll(s),
  errno=2` → `/sys/class/power_supply/` **整个目录为空**（不是读不到，
  是没注册）。
- oplus_chg 栈（chg/symbol/v2/ufcs/qti_battery_debug）全部已加载（ROM
  first-stage 从 vendor_dlkm 的 modules.load 带入），bq27541 主计已绑定
  （`oplus,bq27541-battery`，OPLUS 桥接版）。
- 但 **ADSP（remoteproc1）offline**，ADSP 模块栈（q6_pdr/q6_notifier/
  snd_event/gpr/spf_core/adsp_loader）未加载——rc 的 `on boot` insmod
  路径写的 `/vendor/lib/modules` **在这台设备不存在**（模块全在
  `/vendor_dlkm/lib/modules`，392 个），静默失败。
- 活体验证：从 vendor_dlkm insmod 6 个 ADSP 模块 + `echo 1 >
  /sys/kernel/boot_adsp/boot`（固件 adsp.mdt 在 modem 分区
  firmware_mnt/image，需内核 firmware 路径可达）→ **ADSP running，
  OPLUS_CHG[ADSP] 充电框架立刻活跃**（ICL/AICL 协商）。本会话 gauge 的
  一次性 init 已在 302s 放弃（无法再注册），下个镜像在 30s 前完成此序
  列即可。

### 9.3 WiFi：ADSP + modem（DMS MAC）+ 早期 fs_ready

- 不写 fs_ready 就没有 wlan0；**写了 fs_ready 且 USB gadget 已活跃 →
  设备 panic 重启**（两次复现：无 ADSP 一次、有 ADSP+modem 一次）。
- ADSP 运行后写 fs_ready **不再崩溃**：PCIe/MHI 起、kiwi 固件
  （regdb.bin + bdwlan.elf，来自 firmware_mnt/image/kiwi/）下载成功、
  校准完成（7600ms）、WLFW QMI 连接——最后卡在
  `Unable to get MAC from DMS after retries`：**出厂 MAC 来自 modem 的
  DMS QMI 服务**。
- 活体验证：`echo start > remoteproc3/state`（mss）→ **modem 在
  recovery 里启动成功**（modem.mdt 由 /lib/firmware 软链解析）→ DMS 可用。
- 结论：ROM 的 init.target.rc 在 **post-fs-data（USB gadget 配置前）**
  写 fs_ready——这是唯一活体安全的时序。v4 把 ADSP 启动 + modem 启动 +
  QCA 栈 insmod + fs_ready 全部移入 init.recovery.qcom.rc 的
  post-fs-data。

| 项 | 内容 |
|---|---|
